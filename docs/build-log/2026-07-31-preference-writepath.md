# Preference write path — the substrate fix, and what it did not move

**Date:** 2026-07-31 · **Worktree:** `Memphant-af-w11-writepath` · **Branch:** `af-w11-writepath`
**Cost:** `paid_model_calls: 0`. Regex-derived gold only, local fastembed, local Postgres.

## 0. Headline, stated plainly

The write-path substrate is fixed and the fix is real. **It moved the score by
exactly nothing.**

On the same instrument, the same 1063 probes, the same 257 instances, with the
typed write-router landed and the harness unchanged, MemPhant's
latest-state-wins rate is **0.3123236124176858** — **bit-identical** to the
2026-08-01 measurement — against the BM25 control's **0.3198494825964252**.
ΔLSW **−0.0075**, cluster-bootstrap 95% CI **[−0.0370, +0.0228]**.
Misapplication **0.6717** vs **0.6736**. We still lose to a lexical baseline at
telling a live rule from a dead one, and the loss is the same loss.

That is not a disappointing result, it is a clean one: it isolates the
remaining gap to a single named thing, and it does so with an identity rather
than an argument. **Supersession is now reachable in the substrate and still
unreached on this corpus, because nothing at $0 can produce the subject key.**

**And the size of the prize is now measured, not guessed.** An explicitly
oracle-keyed arm — the instrument's own grouping rule handed to the write path,
therefore *not* comparable to BM25 and marked `decisional: false` — takes
latest-state-wins to **0.5795** and misapplication to **0.3405**
(Δ +0.2672 / −0.3311 against the unchanged arm, cluster CI
[+0.2375, +0.2985] / [−0.3647, −0.2984]). The machinery works: **7198
`supersedes` edges** where the unchanged arm had zero, **0** retired rows ever
recalled. So the missing 27 points of LSW sit behind **one** unbuilt thing: a
producer of subject keys. §4 measures why free ones do not work; §7 names what
does.

## 1. What was built (spec 04 §13)

Three changes, commit `ffa640b8`, all in §13's terms.

**1. `MemoryKind::Preference` minted** (§13.2a), with the governed migration
`memphant_migrations/versions/20260731_006_preference_memory_kind.sql`.
`knowledge` was **not** minted: §13.2c makes it the router-arm name for
`semantic`, and a sixth variant filling the same §0.1 policy row is exactly
what §0.1 rejects.

**2. The typed write-router dispatch** (§13.1), in
`crates/memphant-core/src/lib.rs`:

- `write_router_arm(MemoryKind) -> WriteArm` is an **exhaustive match with no
  `_` arm** (RW-1). Minting a further kind cannot compile until it has an arm.
- `supersedes_own_kind(MemoryKind) -> Option<MemoryKind>` is the lift. The
  supersession target filter was the literal `existing.kind ==
  MemoryKind::Semantic` inside one branch; it now comes from the arm. Because
  an arm can only ever name its *own* kind there, **RW-3 became structural**:
  no dispatch can widen supersession across kinds, and `episodic_arm` provably
  supersedes nothing.
- RW-7: an untrusted caller's `preference` hint degrades to a belief, as a
  `semantic` hint already did.

**3. `MEMPHANT_FACT_EXTRACTION`**, `crates/memphant-runtime/src/lib.rs`,
**default ON** — see §3, where it is measured.

**A real bug fell out of the lift.** Before it, an **Episodic** candidate
carrying an explicit subject would close an open **Semantic** unit's
generation — a cross-kind write, because the target filter named `Semantic`
while the minted unit took the candidate's kind. Regression:
`crates/memphant-core/tests/preference_write_router.rs::an_episodic_candidate_never_supersedes_even_with_an_explicit_subject`.
Attribution below is by bisect, and it is red at the parent commit.

### The migration and its cost

Cheaper than §13.2 anticipated in code, more expensive in *invisible* places.

| Cost | Detail |
|---|---|
| enum + `ALL` | `crates/memphant-types/src/lib.rs`, 2 lines. No exhaustive `match` on `MemoryKind` existed anywhere in `crates/*/src`, so nothing else broke. |
| SQL | two `check (kind in (...))` constraints (`memory_unit`, `scope_policy`). Declared **breaking** and the classifier *computes* it (the file drops a constraint); `schema_compat_revision` moves to this migration. Widening a TEXT+CHECK enum is additive only under `25` §11c's fallback read rule, and the frozen kind enum is the closed Rust reader that rule exempts — an old binary would fail serde decode on a `preference` row, so it must self-gate at boot. |
| generated artifacts | `examples/evals/trace-schema.v1.json`, `mcp/memphant.tools.v1.json`, `openapi/memphant.v1.json`, all regenerated by their own generators, none hand-edited. |
| **the trap** | **two hardcoded five-kind lists** resolved the scope policy (`lib.rs`, `store.rs`). A kind absent there gets no source, `context.allows` denies it, and the unit is **invisible to both the compiler snapshot and recall** — the write lands and nothing can see it. That is how minting first failed, *silently*, in a green test. Both now iterate `MemoryKind::ALL`. |
| no change needed | `agent_level_allows_memory_kind` already restricts L1+ agents to episodic/procedural/resource, which correctly denies an agent a standing user preference (§13.2a). |

The trap is the transferable lesson: **RW-1's exhaustive match protects the
dispatch, not the enumerations elsewhere.** A `MemoryKind::ALL` iteration is
total; a hand-written list is a silent partial function.

## 2. The measurement

Same instrument, same prereg (`docs/build-log/2026-08-01-preference-lane-prereg.md`),
same analysis: cluster bootstrap over the **257 instances**, 10,000 resamples,
seed 20260801. Probes are nested (mean 4.1 per instance) and are never treated
as 1063 independent observations.

### Arm A′ — router landed, harness unchanged

| endpoint | MemPhant (A′) | BM25 (B) | Δ (A−B) | cluster CI95 | perm p |
|---|---|---|---|---|---|
| **Appropriate Application** (= LSW) | **0.3123** | **0.3198** | −0.0075 | [−0.0370, +0.0228] | 0.657 |
| **Misapplication** | **0.6717** | 0.6736 | −0.0019 | [−0.0318, +0.0288] | 0.950 |
| Neither returned | 0.0103 | 0.0019 | +0.0085 | [+0.0020, +0.0157] | 0.029 |

Both directions are named, and the third bucket is reported, so a suppression
win cannot pass as an application win. The only significant difference is
**neither-returned, and it runs against MemPhant.** Descriptively MemPhant is
also worse at surfacing the current rule at all: hit@10 0.786 vs 0.933,
hit@1 0.231 vs 0.268.

Exact McNemar p = 0.674 on 276 discordant probes (b=134, c=142), reported as
the anti-conservative reference it is. Computed MDE at 80% power, n=1063,
psi=0.2596: **0.0445**, via `scripts/instrument_power.py`.

**Every one of those figures is bit-identical to 2026-08-01.** Not "close" —
identical to the last digit of a float. That is itself a result: the substrate
change is behaviourally inert on the unchanged path, and the harness is
deterministic enough to prove it.

### Why it is inert, read from the run's own database

`memory_edge` by kind: **empty**. `memory_unit` by state: **`active` = 8147, all
of them.** By kind: **`episodic` = 8147**. Units with a predicate: **0**.
`retention_tier`: `hot` × 8147. Corpus verified compiled from the bench
superuser credential before scoring: 8147 episodes, 8147 with units, 0 pending,
0 failed.

The compiled path is unchanged because the candidate is unchanged. `compile_job`
still emits one `Episodic` candidate with `fact_key: None` and no subject; that
mints an auto content-hash key; `has_explicit_subject` is false; the branch is
skipped before the router is ever consulted. The router removed the *second*
lock (`kind == Semantic`). **The first lock — no subject — is still shut**, and
it is shut for a reason nobody has yet paid for.

## 3. The flag arm: the producer exists, and it mines nothing here

The claim that a deterministic subject-key producer already exists behind an
unwired flag is **true**, and I verified all three parts:

- `extract_fact_candidates` (`service.rs:6592`) sets `subject: fact.family`,
  `predicate: fact.subject_phrase` → the stable key `{scope}:{family}:{phrase}`
  via `derive_fact_key`. Deterministic, hand-rolled token scans, no regex
  dependency, **no LLM, no network**. Its candidates carry `kind: None` →
  default `Semantic`, so they *can* enter the supersede branch.
- Gated on `fact_extraction_enabled`, default `false` (`service.rs:3454`).
- The **only** caller of `with_fact_extraction_enabled` in the tree was
  `crates/memphant-eval/src/bench_lme.rs:885`. Zero server or config wiring.

So it was wired: `MEMPHANT_FACT_EXTRACTION`, default ON.

**And on MemoryCode it extracts almost literally nothing.** Full arm, all 1063
probes, measured on the arm's own scratch DB before it was dropped:

| Arm F diagnostic | value |
|---|---|
| `memory_unit_by_kind` | `episodic` 8147, **`semantic` 2** |
| units with a predicate | **2 of 8149** |
| `memory_edge` by kind | **empty** |
| `memory_unit_by_state` | `active` 8149, nothing superseded |

**Two facts mined from 8147 episodes.** The score is consequently
**bit-identical** to Arm A′: LSW 0.3123236124176858, MR 0.6716839134524929,
hit@k 0.7855126999059266. The A′-vs-F paired comparison is
`ΔLSW = 0.0`, cluster CI `[0.0, 0.0]`, **0 discordant probes out of 1063**
(`analysis-f-vs-a.json`, marked `decisional: false` because n_d = 0 is below
the exact test's rejection floor — a zero delta on zero discordance is an
identity, not a null result).

Two independent structural reasons, both read off the code:

1. **`extract_facts` mines only user turns.** `parse_turn` splits `role: content`
   and `continue`s unless the role normalizes to `"user"`. Every MemoryCode
   dialogue line is `Luis: …` / `Kiyotaka: …`, so **every turn is skipped**; only
   a line that does not parse as `role: content` at all reaches the matcher
   through the non-role prose fallback, which is where the surviving 2 came
   from.
2. **Every pattern is first-person self-report** — `match_superlative` requires
   "my [all-time] favorite", `match_my_noun_is` requires "my <noun> is",
   `match_preference_verb` requires a leading "I". MemoryCode's instructions are
   second-person mentor directives: *"Start attribute names with 'q_'."*

The flag is still right to have wired — an unreachable supersession default is
not a memory substrate, and the plumb costs nothing. It is simply **not the
lever for this instrument**, and no full-corpus delta is claimed for it beyond
the measured zero.

## 4. Can the key be derived from the text at $0? Measured: no

Before conceding to an oracle, the honest alternative was measured. A
gold-independent key derived from the **session body** (never from the `topic`
metadata the gold rule uses), over all 1063 gold groups, scored on whether the
sessions in a group share a derived key:

| rule | groups recovered |
|---|---|
| quoted-literal-stripped content-word set of any imperative sentence | 8 / 1063 = **0.008** |
| the single content word preceding the quoted literal | 221 / 1063 = **0.208** |
| the two preceding content words | 118 / 1063 = 0.111 |
| the three preceding content words | 70 / 1063 = 0.066 |

Sessions **restate a convention in paraphrase** — the update session opens
*"Remember when I mentioned that we use a specific naming convention for
variables and attributes?"* — so lexical alignment with the original
declaration is absent by construction. **Deriving a preference key from
conversational text is an extraction problem, and extraction is a `reflect`
stage-1 LLM job, which this lane's $0 budget forbids.**

This is the finding that reframes the lane. It is not that supersession is hard
to implement; it took ~40 lines. It is that **nothing free can decide what two
utterances are about.**

## 5. State machine vs ranking: the oracle arm

To separate "the state machine works" from "ranking uses the state", an
explicitly **oracle-keyed** arm was run: the harness supplies the instrument's
own supersession group key as the subject.

**This arm is not comparable to the lexical control and is not evidence of
retrieval quality.** The key is derived from the same `topic` field the gold
labels are, so the grouping is handed to the system. It answers one mechanism
question and no other: with a correct chain, does the machinery actually fire
end-to-end through Postgres, and does recall then use the state?

Full bank, 1063 probes, 257 instances (`analysis-p-vs-a.json`,
`decisional: false` — because the arms are not comparable, not because of
power):

| endpoint | Arm P (oracle-keyed) | Arm A′ (unchanged) | Δ | cluster CI95 | perm p |
|---|---|---|---|---|---|
| **Appropriate Application** (= LSW) | **0.5795** | 0.3123 | **+0.2672** | [+0.2375, +0.2985] | 1.0e-4 |
| **Misapplication** | **0.3405** | 0.6717 | **−0.3311** | [−0.3647, −0.2984] | 1.0e-4 |
| Neither returned | 0.0734 | 0.0103 | +0.0630 | [+0.0466, +0.0791] | 1.0e-4 |

hit@1 0.328 vs 0.231, hit@10 0.840 vs 0.786.

**Both directions move, in the right direction, and they are not each other's
mirror.** Misapplication nearly halves. That is the suppression working. But
+0.063 of the mass moved into **neither-returned**, so part of the
misapplication drop is the retired rule being suppressed *without* the live one
taking its place — which is exactly why the third bucket is reported.

Three things this settles:

- **The state machine fires, at scale, through Postgres.** `memory_edge`:
  **7198 `supersedes` + 3599 `contradicts`** rows, where the unchanged arm had
  **zero edges of any kind**. 3599 `superseded` units, **0 of them with an open
  transaction**. 10,694 `preference` units across 257 scopes.
- **Recall uses the state.** `remainders_recalled` = **0**: no valid-time-closed
  row ever reached a recall result, so the bitemporal exclusion holds and the
  scoring identity is exact.
- **The ceiling is below 1.0 for a corpus reason, not a bug.** A session often
  declares several conventions; retiring one leaves the *session* live under
  another key, and the scoring identity is the session. A stale session can
  therefore still be returned legitimately.

**So: which of state-machine vs ranking still fails?** The state machine does
not. It transitions, edges, and is honoured on read. What remains is that even
a perfect chain reaches **0.5795**, below the 63–68% deterministic band in §7 —
and the residual 0.34 misapplication is not a supersession failure but the
session-granularity of the identity plus ordinary retrieval error. **Ranking is
the smaller remaining problem; producing the key is the larger one, and it is
the one this arm cheats on.**

## 6. Two ranking defects verified, and one of them is not binding here

Reported separately, as asked, rather than folded into the result.

**`temporal_score` is binary and its tie-break is alphabetical — and it is
inert on this lane.** Verified: `temporal_score` (`lib.rs:10916`) returns `1.0`
for *every* Active Semantic unit when the query contains `current`, `latest` or
`now`, and the fusion tie-break (`lib.rs:7264`) is `left.0.body.cmp(&right.0.body)`
— ordering by first character of the body. Real defect. **But 0 of 1063
MemoryCode probe queries contain any of those three tokens** (counted from the
parquet), and every unit in the unchanged arm is `Episodic`, not `Semantic`. So
`temporal_score` is `0.0` on all 8147 units for all 1063 probes and **cannot be
the binding constraint on this lane.** It may well be binding elsewhere.

**`exact_score` is diluted by the scope UUID.** Verified: `exact_score`
(`lib.rs:10722`) tokenizes the whole `fact_key`, and `derive_fact_key` prefixes
it with `{scope_id}:` — a hyphenated UUID contributes five constant tokens to
every denominator, so a perfect subject match scores well below its intended
magnitude. Real, not mine, not fixed here, and noted so a weak Exact signal is
not attributed to this change.

## 7. The ceiling this fix reaches, named

*Control-Plane Placement Shapes Forgetting* (arXiv:2606.15903v2), **relayed by
the coordinating session and not independently verified in this worktree**,
measures 13 third-party memory systems on one 385-case adversarial harness:

- **deterministic primitives — 63.4–68.3%.** This is the band a keying fix
  lands in.
- inscribe-time LLM — recovers canonicalisation, **0%** on intent-aware
  deletion and prefix collision.
- **mutation-time LLM hook — 91.7–93.2%**, +22.6 to +24.1pt on non-primitive
  cases, ~$0.17 per 385 mutations, 2.3 s per mutation, **recall hot path
  untouched** (64–74 ms).

The load-bearing claim is that **identifier variants and intent-aware deletion
are not recoverable by any hash or keying scheme, by construction.** So this
work reaches the deterministic baseline; it is not the frontier, and the build
log should not be read as claiming otherwise. §4's measured 0.008/0.208 is that
same wall met from a different direction.

The hook was **not built** (out of scope). The router shape deliberately leaves
room for it: `supersedes_own_kind` returns the *kind* an arm may close, never
the set of units, so target selection remains a separate step on the
supersede/purge path — off the recall hot path, and outside RW-2's
no-LLM-in-the-router rule, which governs the dispatch and not a mutation-time
refinement.

*Ground Truth First* (arXiv:2607.21962), same provenance caveat: facts with
weak writes failed downstream QA 24.2% of the time versus 1.6% for clean
writes, OR 19.6 — third-party corroboration that write quality is the dominant
factor, which is why this lane was chosen.

## 10. What this leaves for whoever picks it up

- **Binding constraint, named:** nothing on the served write path produces a
  subject key for a restated convention. Not the router (fixed), not
  `kind == Semantic` (lifted), not recall's supersession exclusion (correct and
  now demonstrably live — 0 retired rows recalled across 1063 probes), not
  `temporal_score` (inert here, 0/1063 queries). The oracle arm prices the gap
  at **+0.267 LSW / −0.331 misapplication**.
- **The residual after a perfect key is a different, smaller problem.** Even
  oracle-keyed, LSW is 0.5795 and 0.34 of probes still misapply — driven by the
  session-level scoring identity (one session can declare several conventions,
  so retiring one leaves it live under another) rather than by supersession.
  Do not spend ranking effort there before the key exists.
- The next lever is a **mutation-time control-plane hook** on the
  supersede/purge path (§7). The seam is open; the decision is not mine.
- `retention_tier` remains inert (`hot` × 8147). This run gives **no** evidence
  that tiering would move latest-state-wins: demotion moves storage, it does not
  retire a rule.
- No checkbox, default, cutover or SOTA claim moves. The one default that did
  change is `MEMPHANT_FACT_EXTRACTION`, and §3 measures it at zero effect on
  this instrument.
